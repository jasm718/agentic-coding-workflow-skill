# 选例与确认

## 从改动到实际用例

读取源码、调用关系和业务契约，识别直接影响及通过鉴权、共享数据、接口、状态或部署关联的模块。模块标签表示用例主归属，不是完整依赖图，不能仅按改动目录机械选例。

以项目 E2E 列表为入口，用源码和 Runner 的实际收集/预览结果核对。使用稳定 ID、模块和集合元数据选择，不从抽象名称猜测。只读取文件或调用确认不会执行用例的预览命令；需要接触设备/模型的“检查”留到确认后执行。

| 用途 | 选择原则 |
|---|---|
| 本次功能 E2E | 能直接证明本次功能/修复行为的已实现用例，既可以新增也可以复用 |
| 回归 E2E | 覆盖受影响模块及关联模块的原有行为；必要时选核心冒烟作为基础可用性检查 |

“功能验证”和“回归”是本次运行的用途，不要求修改用例原有 smoke/regression 标签。回归本身并不等于 E2E；本 Skill 的主要选例对象是 E2E，已有快速测试结果及流水线附带测试应另外说明，不混入 E2E 数量。

## 开发与发布场景

- 开发验证：以用户明确的本次改动为范围，选直接功能用例与必要关联回归。不要默认每次全量，也不要沿用 dev 清单里上次开发遗留的无关编号。
- 发布验证：明确上次发布基线和候选提交，分析累计变化；按项目流程执行核心冒烟，再验证受影响及关联模块。没有可靠基线先询问，不随意选一个成功构建代替。
- 跨模块验证应包含需要的 web、desktop、integration 用例，不能因脚本只支持 Web 就称全部覆盖。
- 完整 E2E 只在项目流程、用户选择或已说明的变化风险要求时纳入确认方案，不因筛选无结果而自动扩大范围。
- 缺少必要用例时列出缺口和影响，可提议交给 write-tests 补充。其余可执行部分能单独验证时明确价值与限制供用户确认，不能用相关模块名称代替真实覆盖。

先形成两类列表，再按 ID 去重；同例作为功能验证和回归都被选中时标注双重理由，实际只跑一次。复用先前结果必须确认相同产物、环境和有效状态，不能跨版本或跨部署直接认定通过。

## 用户确认方案

先给简短环境摘要，再展示具体用例：

| 类别 | 用例 ID | 模块 / 功能 | 用例名称 | 选择理由 |
|---|---|---|---|---|
| 本次功能 E2E | 项目真实 ID | 本次修改功能 | 真实用例名称 | 直接验证修改后的行为 |
| 回归 E2E | 项目真实 ID | 关联模块功能 | 真实用例名称 | 验证关联已有行为未退化 |

给出两类数量和去重后的实际执行数量；没有某类时解释原因。摘要明确：

- 改动基线、候选提交/本地状态、测试环境实际版本。
- 本地执行目录和命令，或 Jenkins 实例、任务、节点、上游构建及参数。
- 是否构建、安装或部署，是否还有单元/功能测试、额外 E2E 或发布副作用。
- 已知缺口、执行顺序、报告入口的获取方式。

确认前不修改执行清单。用户确认后依据项目机制写入真实 ID 或传递模块/编号参数，预览实际选择与确认表一致。预览发现额外用例、未知编号、重复或遗漏时先解决选择问题，不带着不一致触发运行。

如果已有 Jenkins 任务不能表达确认范围，或上游归档清单不同于本地拟选清单，明确阻碍。不能只改本地 dev-cases.json 就认为旧 CI 产物里的清单也变了。需要新构建或变更任务时提出具体方案；未确认前不执行扩大的流程。

用户明确确认后继续，不重复问“是否开始”。环境、版本、范围或副作用变化才重新确认变化部分，普通轮询和日志读取不需要重复确认。
