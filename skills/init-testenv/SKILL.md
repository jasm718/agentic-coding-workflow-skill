# 初始化测试工具

交付可以开始编写第一条测试的基础工具、工程结构和使用说明。初始化不等于建设完整测试体系，不预先实现尚无实际用例支撑的能力。此 Skill 只包含说明，不携带 assets 工程或可复制的测试项目。

## 检查并确认范围

先确认工作目录、适用的 AGENTS.md、语言和组件，读取现有测试、依赖、配置及执行命令。已有能力直接复用，保留现有测试和无关改动。

把发现的事实与仍需决定的事项分开。只有缺口会影响初始化时才集中询问，通常包括：

- 本次需要初始化哪些测试层级和组件？
- E2E 需要浏览器、桌面客户端，还是两者共同操作？
- 项目是否已有必须沿用的工具和目录约定？

用户已明确的选择直接采用；普通实现细节依据项目惯例处理。无需为了初始化追问所有测试机、业务账号、API 地址或未来 fixture。暂时不确定的信息写为后续接入项，不编造默认值，也不因此阻塞独立的基础工作。

## 初始化五项内容

1. **项目与范围**：明确要处理的组件、测试层级和运行端。用户只要求方案时不改文件。
2. **目录与命名**：读取 [最小结构与职责](references/project-structure.md)，约定单元测试位置、`tests/functional/` 与 E2E 业务模块布局。不批量创建模块空目录、空测试或占位 helper。
3. **基础工具**：沿用或安装对应语言的测试执行器。E2E 固定采用 Midscene AI 操作、Playwright 浏览器接入、Midscene Test Runner 编排。核对已安装版本 API；新依赖按官方资料选择相容版本，记录必要依赖和锁文件。业务需要的额外依赖以后再加。
4. **基础配置与入口**：配置文件发现规则及按层级、文件或单例执行的入口。E2E 只建立所需运行端的最小接入骨架和基础可视报告输出位置。命令写好供用户以后运行，本次不执行。
5. **简短说明**：在项目已有测试说明中写清目录职责、命名、第一条测试如何添加、从哪个目录手动运行什么命令，以及哪些环境信息需要后续补充。不维护第二套重复说明。

## 本次不做

- 不接入 CI/CD，不创建或修改 Jenkinsfile、流水线、分支触发、部署脚本，也不配置 JUnit XML 等 CI 报告。
- 不执行单元、功能、集成、E2E 或报告自检，不自动运行示例，不调用模型、启动浏览器/客户端或连接被测系统验证。
- 不编写业务测试或演示测试，不规划冒烟/回归范围，不生成开发执行清单。
- 不提前实现业务 fixture、登录封装、API helper、mock、数据库隔离或复杂报告聚合。具体配置和能力在 write-tests 编写真实用例时按需补充，出现复用需求再提取。
- 不构建、部署、提交或推送产品代码。也不删除项目已有的报告、测试或流水线来“符合初始化规范”。

## 完成检查与交付

只做静态检查：配置格式能解析、声明的脚本及引用路径存在、依赖声明和锁文件一致、入口与发现规则匹配约定。可以读取已安装依赖的版本/API，不通过导入测试模块或调用测试执行器进行验收。安装依赖前检查项目生命周期脚本，避免安装过程顺带执行测试或业务操作。

从零开始允许没有用例；使用说明明确“尚无用例，未执行测试”。不写假用例凑成功，不把执行器的空收集、错误或跳过包装成通过。保留执行器原有失败退出码。

交付已准备的工具、改动文件、手动执行命令、待补配置与静态检查结果，并明确说明本次未执行测试。后续用例设计与实现可交给 write-tests，测试范围确认及实际执行可交给 run-tests；二者不是初始化的强制依赖。
