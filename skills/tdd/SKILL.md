# 测试驱动开发

<principle>

## 理念

**核心原则**：测试应该通过公开接口验证行为，而不是验证实现细节。代码可以完全重写；测试不应该因此改变。

**好的测试是偏集成风格的** 。它们通过公开 API 走真实代码路径。它们描述系统“做什么”，而不是“怎么做”。好的测试读起来像规格说明，比如“用户可以用有效购物车结账”会清楚说明系统具备什么能力。这类测试能经受重构，因为它们不关心内部结构。

**坏的测试会耦合实现** 。它们 mock 内部协作者、测试私有方法，或通过外部手段验证结果（比如直接查询数据库，而不是使用公开接口）。警告信号是：你重构了代码，行为没有改变，但测试却失败了。如果只是重命名内部函数就导致测试失败，那这些测试测的是实现，不是行为。

参考 [tests.md](tests.md) 查看示例，参考 [mocking.md](mocking.md) 查看 mock 指南。

</principle>

<anti-pattern>

## 反模式：横向切片

**不要先写完所有测试，再写所有实现。** 这是“横向切片”：把 RED 理解成“写所有测试”，把 GREEN 理解成“写所有代码”。

这会产生 **垃圾测试**：

- 批量写出来的测试验证的是 _想象中的_ 行为，而不是 _实际的_ 行为。
- 你最终会测试事物的 _形状_（数据结构、函数签名），而不是面向用户的行为。
- 测试会对真实变化失去敏感度：行为坏了它们还通过，行为没问题它们却失败。
- 你会跑得太远，在理解实现之前就过早承诺测试结构。

**正确做法**：通过 tracer bullet 做纵向切片。一个测试 → 一个实现 → 重复。每个测试都基于上一轮循环学到的东西来写。因为你刚写完代码，所以你最清楚哪些行为重要，以及该如何验证。

```text
错误（横向）：
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正确（纵向）：
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

</anti-pattern>

<workflow>

## 工作流

### 1. 规划

写任何代码之前：

- 与用户确认需要哪些接口变更。
- 与用户确认要测试哪些行为，并排优先级。
- 识别 [深模块](deep-modules.md) 的机会：小接口，深实现。
- 为 [可测试性](interface-design.md) 设计接口。
- 列出要测试的行为，而不是实现步骤。
- 让用户批准计划。

询问：“公开接口应该是什么样？哪些行为最重要，最需要测试？”

**你无法测试所有东西。** 和用户确认到底哪些行为最重要。把测试精力放在关键路径和复杂逻辑上，而不是每一个可能的边界情况。

### 2. Tracer Bullet

写一个测试，只确认系统的一件事：

```text
RED:   为第一个行为写测试 → 测试失败
GREEN: 写最少代码让测试通过 → 测试通过
```

这是你的 tracer bullet：证明这条路径可以端到端跑通。

### 3. 增量循环

对每个剩余行为：

```text
RED:   写下一个测试 → 失败
GREEN: 写最少代码让它通过 → 通过
```

规则：

- 一次只写一个测试。
- 只写足够通过当前测试的代码。
- 不要预判未来测试。
- 让测试聚焦可观察行为。

### 4. 重构

所有测试通过后，查找 [重构候选项](refactoring.md)：

- 提取重复。
- 加深模块：把复杂度移动到简单接口背后。
- 在自然适用的地方应用 SOLID 原则。
- 思考新代码暴露了现有代码的哪些问题。
- 每一步重构后都运行测试。

**绝不要在 RED 状态下重构。** 先回到 GREEN。

## 每轮循环检查清单

```text
[ ] 测试描述行为，而不是实现。
[ ] 测试只使用公开接口。
[ ] 测试能经受内部重构。
[ ] 代码只为当前测试保持最小实现。
[ ] 没有添加猜测性的功能。
```

</workflow>
