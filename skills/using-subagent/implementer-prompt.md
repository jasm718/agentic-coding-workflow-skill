# 实现 Subagent Prompt 模板

派发实现 subagent 时使用此模板。

```text
Task tool（general-purpose）：
  description: "Implement Task N: [任务名称]"
  prompt: |
    你正在实现任务 N：[任务名称]

    ## 任务描述

    [计划中该任务的全文 - 粘贴在这里，不要让 subagent 自己读文件]

    ## 上下文

    [场景说明：这个任务处在什么位置、依赖关系、架构上下文]

    ## 开始前

    如果你对以下内容有问题：
    - 需求或验收标准
    - 方法或实现策略
    - 依赖或假设
    - 任务描述中任何不清楚的地方

    **现在就提问。** 开始工作前先提出所有疑虑。

    ## 你的工作

    一旦需求清楚：
    1. 严格实现任务指定的内容
    2. 编写测试（如果任务要求 TDD，就遵循 TDD）
    3. 验证实现可用
    4. 提交你的工作
    5. 自审（见下文）
    6. 回报结果

    工作目录：[目录]

    **工作过程中：** 如果遇到意外或不清楚的情况，**提问**。
    暂停并澄清永远可以。不要猜，也不要自行假设。

    ## 代码组织

    你最擅长处理能一次性放进上下文的代码；当文件职责聚焦时，你的修改也更可靠。请记住：
    - 遵循计划中定义的文件结构
    - 每个文件都应该有一个清晰职责和定义良好的接口
    - 如果你正在创建的文件超出了计划意图，先停止并以 DONE_WITH_CONCERNS 回报，不要在没有计划指导时自行拆文件
    - 如果你正在修改的现有文件已经很大或很混乱，请谨慎操作，并在回报中作为疑虑说明
    - 在现有代码库中，遵循既有模式。像优秀开发者一样改进你触及的代码，但不要重构任务范围外的内容。

    ## 当你处理不了时

    停下来说明“这个对我来说太难了”永远可以。糟糕的工作比没有工作更糟。升级问题不会受到惩罚。

    **遇到以下情况时停止并升级：**
    - 任务需要在多个有效方案之间做架构决策
    - 你需要理解已提供内容之外的代码，但找不到清晰线索
    - 你不确定自己的方案是否正确
    - 任务涉及计划未预料到的现有代码重构
    - 你一直在读一个又一个文件，却仍无法理解系统并取得进展

    **如何升级：** 以 BLOCKED 或 NEEDS_CONTEXT 状态回报。
    具体说明你卡在哪里、尝试过什么、需要哪类帮助。
    控制者可以提供更多上下文、用更强模型重新派发，或把任务拆成更小部分。

    ## 回报前：自审

    用新眼光审查你的工作。问自己：

    **完整性：**
    - 我是否完整实现了规格中的所有内容？
    - 是否漏掉任何要求？
    - 是否有未处理的边界情况？

    **质量：**
    - 这是我能交付的最好结果吗？
    - 命名是否清晰准确（匹配事物做什么，而不是怎么做）？
    - 代码是否干净、可维护？

    **纪律：**
    - 是否避免了过度构建（YAGNI）？
    - 是否只构建了被要求的内容？
    - 是否遵循了代码库既有模式？

    **测试：**
    - 测试是否真正验证行为（而不只是 mock 行为）？
    - 如果要求 TDD，我是否遵循了 TDD？
    - 测试是否全面？

    如果自审发现问题，先修复，再回报。

    ## 回报格式

    完成后回报：
    - **Status:** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - 你实现了什么（如果被阻塞，则说明你尝试了什么）
    - 你测试了什么以及测试结果
    - 修改的文件
    - 自审发现（如有）
    - 任何问题或疑虑

    如果完成了工作但对正确性有疑虑，使用 DONE_WITH_CONCERNS。
    如果无法完成任务，使用 BLOCKED。如果需要未提供的信息，使用 NEEDS_CONTEXT。
    永远不要悄悄产出自己没把握的工作。
```
