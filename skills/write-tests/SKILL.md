# 编写与验证测试

依据明确的预期行为实现有价值的测试，交付可执行代码和实际验证结果。读取适用的 AGENTS.md、测试规范、已有计划、相关实现、fixture、Node、执行命令与 CI/CD 选择方式。

用户只要求计划时不写代码；用户只要求补测试时不顺带改变产品行为。本 Skill 自行完成必要的设计与确认，不依赖其他规划 Skill 或外部 qa-test-planner 安装。

## 阶段一：设计并由用户确认

先检查是否有用户已经明确确认、且与当前需求一致的用例设计。有则直接进入阶段二，不重复请求确认；只有计划文件存在或用户说“补测试”，不等于该设计已经被确认。

没有已确认设计时，读取 [用例设计与确认](references/test-case-design.md)，参考其中从 qa-test-planner 提炼的规则，完成给人阅读的用例设计。先按“模块 → 功能”列出用例总览、数量、层级、优先级及新增/修改/复用关系，再写清每例前置条件、输入、操作步骤、预期结果和清理。不能用实现代码或抽象标题代替设计。

展示完整设计及未覆盖风险后，明确请求用户确认并等待回复；说明这是本 Skill 的“设计确认后再实现”要求，并链接本文件。未确认前可阅读代码、分析和整理设计，不创建或修改测试源码、可执行 YAML、fixture、Node 或执行清单，不运行测试。允许更新用户要求的计划文档；计划用例不计入已实现 E2E 列表。

用户要求调整时先修订设计再确认；只确认部分则只实现该部分。等待时间、沉默或“已阅读”不构成确认。用户在现有会话中已给出的明确批准继续有效，不要求特定确认措辞。

## 阶段二：实现已确认用例

按照已确认的行为、层级和范围编写测试。普通实现选择、节点复用和不改变业务目标的重构无需反复确认。新增验证目标、删除覆盖或改变预期结果等实质变化，要先展示差异并等待对变更部分的确认，不继续实现未确认内容。

用户明确指定删除某些已有用例，且删除对象和范围已经清楚时，可视为对该删除的确认。仅同步 E2E 列表、修复链接或统计且不改变测试行为时直接完成，不另造用例设计审批。

## 实施准则

1. 找到现有相同或相近用例，优先修改或复用；必要时新增。按能够充分验证行为的最低层实现，不强制每次写三层。
2. 单元测试遵循语言和组件约定；功能/集成测试放到项目约定的 `tests/functional/<组件或模块>/`；E2E 按业务模块放入 `tests/e2e/cases/`。已有项目规则优先。
3. 使用真实被测逻辑与明确数据，mock 非被测网络、时钟或外部服务边界。不把被测组件全部 mock 后只断言调用次数，不以 HTTP 200 代替业务断言。
4. 验证正常、异常、边界、权限或状态变化中与改动相关的部分。数据库使用隔离数据，异步规则使用受控时钟或有截止时间的条件等待。
5. Bug 回归尽可能证明原缺陷会失败、修复后通过。不能安全还原原版本时说明未完成反证；语法错误、模型故障或环境故障不算复现产品 Bug。
6. E2E 具体编写和报告要求见 [E2E 编写](references/e2e-authoring.md)。缺少单个业务节点时补充，缺少整个运行框架则指出初始化需求，不擅自替换技术栈。
7. 每次新增、删除、改名、移动 E2E 或改变验证行为、运行端、集合标签，都同步维护项目的 E2E 用例列表，无需用户另行提醒。以实际收集结果和测试代码为准，具体维护规则见 E2E 编写文档的“用例列表维护”。

## 验证

确认编写不自动授权实机测试或部署。按任务已有的执行授权验证：通常先检查类型、收集和列表一致性，再运行获准的相关快速测试；选例或报告改动做对应离线验证。已通过检查不无理由重复。真实 E2E 要确认当前代码已加载或安装在目标环境、资源专用，并在用户授权范围内执行；未执行的项目如实标明。

失败时结合步骤、时间、截图、服务日志区分产品、测试脚本、模型调用和环境问题。不能通过吞异常、删除断言、无限重试、随意加长休眠或改为跳过制造通过。清理失败应保留，未执行不等于通过。

实现后对照已确认设计逐项交付，检查用例能被 CI/CD 收集，用例列表与实际可执行用例一一对应。新增 E2E 按计划设置模块与集合标签；删除时同步移除 dev 等执行清单中的失效引用，用户要求准备 dev/release 验证时再选择本次完整执行范围并预览。不得在完成后才告知用户未经确认的实质性范围变化。

交付修改的测试文件、验证行为、所属集合、更新后的 E2E 用例列表入口及总数、实际执行结果和未验证项。没有 E2E 变更时无需修改其列表。提交、推送、构建部署及触发 Jenkins 按用户已有授权执行，不由“补测试”自动扩大授权。

用户需要运行本次功能及回归 E2E 时，可由 run-tests 确认实际版本、环境、范围和执行方式后运行。用例设计获准编写不代替执行方案确认；已经明确批准同一执行方案时不重复询问。
