# 用例设计与确认

本文件参考 qa-test-planner 的目标、前置条件、输入、动作与预期、优先级和后置清理结构，并按三层自动化测试流程调整。规则已自包含，不要求另装该 Skill 或访问作者的桌面目录。

## 用户应能看懂什么

按业务模块和具体功能组织，让用户看懂：这次测什么、为什么测、共有多少用例、如何判断成功、哪些没有覆盖。先给总览，再给必要步骤；不要用一串脚本名、Node 名或 mock 细节替代业务说明。

| 模块 / 功能 | 用例名称 | 层级 | 优先级及理由 | 新增 / 修改 / 复用 | 预期结果 |
|---|---|---|---|---|---|
| 用户管理 / 停用用户 | 停用后再次登录被拒绝 | E2E | 高：防止停用账号继续访问 | 新增，待实现 | 登录失败并显示明确提示，不能进入受保护页面 |

总览写明计划用例总数及各层数量，复用用例单独计数，不把一个用例的多个步骤算成多个用例。新增用例可用临时设计序号，正式 E2E ID 实现时按项目机制分配；已有用例引用真实 ID 和源文件。

## 每例的必要信息

- **模块、功能和目标**：哪个场景、什么操作、预期业务结果；名称具体且无需读代码也能理解。
- **层级和变更方式**：单元、功能/集成或 E2E，说明新增、修改、复用或删除，以及原因。
- **优先级**：按实际业务影响，沿用项目标准；重要用例不自动等于 E2E 或核心冒烟。
- **前置条件及数据**：角色、初始状态、隔离要求、必要环境和有意义的输入；只写角色和凭据来源，不写真实密码。
- **步骤与预期**：每个关键动作对应可观察的结果，包含需要验证的状态变化。简单规则可用输入/输出表，复杂业务链路按步骤描述。
- **后置状态与清理**：哪些数据应保留，哪些本例资源要回收或恢复。
- **关联与范围**：关联需求或 Bug、复用依据，以及必要的集合建议；不把未实现用例加入可执行清单。

例如“停用后再次登录被拒绝”：

1. 前置：独立普通用户处于启用状态、无已登录会话，测试管理员可修改该用户。
2. 管理员停用该用户；预期列表中该用户显示停用，其他资料不变。
3. 该用户从登录界面尝试登录；预期提示账号停用，不能进入受保护页面。
4. 后置：恢复或删除本例专用账号；不操作其他账号。

“已有登录会话是否立即失效”是另一个业务契约，若未明确则列为待确认，不能顺手添加断言或声称该例已经覆盖。

## 设计取舍

优先用足以证明行为的最低层，不强制三层都写。按真实风险选正常、异常、边界、权限和状态变化，不套固定数量、耗时、通过率或性能阈值。一例只围绕一个业务目标，跨端链路可以包含多个步骤。

Bug 设计应说明原缺陷的触发条件和正确结果；已有测试足够就复用。关键被测动作必须发生，不能准备阶段直接制造最终结果后只断言结果存在。缺少业务约定时明确问题，不让 AI 替用户决定。

不照搬 qa-test-planner 中与本任务无关的 Figma 校验、手工执行历史表、固定发布门槛或明文密码字段。测试设计不混入自动部署授权。

## 确认与交接

设计展示后请求用户确认，等待明确答复，再生成代码。确认针对可审阅的具体用例，不能先问一句“可以写测试吗”就算确认未来未知的设计。用户在已有会话或计划审阅中已确认同一方案时，直接复用，不重复审批。

若用户要求保存设计，沿用项目已有计划文档，标明待确认或已确认；引用用户确认的内容或计划版本，不虚构已批准状态。工程师接手应能直接根据设计实现，而不重新猜测行为。

未经确认的新增或变更部分不能实现；普通实现细节不需要重新走设计确认。代码完成后按设计序号/已有 ID 对照源文件、正式 ID、实现情况和验证结果，便于用户核对是否漏写或偏离。
