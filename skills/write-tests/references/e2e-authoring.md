# 编写 Midscene E2E

本文件用于实现已确认的用例设计。没有明确确认时，先按主 Skill 的设计阶段向用户展示用例并等待确认，不提前创建 YAML、Node 或 fixture。

## 先确认框架能力

读取项目 E2E 说明、Runner 配置、Node 注册和 schema、setup 上下文、fixture、环境字段以及报告逻辑。沿用 Midscene AI 操作、Playwright 浏览器接入、Midscene Test Runner 编排；按已安装版本调用 API，不从名称猜测节点参数。

通用节点足够时只写 YAML，缺少业务能力时在 `nodes/<模块>.ts` 增加并注册。登录、API 路由和清理方式来自真实项目实现，不预置其他产品的接口与凭据。

## 用例组织

- 目录为 `tests/e2e/cases/<业务模块>/`，每文件一例；名称为 `【模块】具体操作和预期结果`。
- 稳定编号独立于目录、运行端和集合，移动或改名保留编号；新例通过项目生成器分配，合并分支后检查冲突，不回收已删除编号。
- 元数据包含 ID、`module:<业务模块>`、运行端和 `smoke`/`regression`。运行端区分 web、desktop、integration，后端或 Agent 参与不自动等于多端 UI 用例。
- 草稿和正式用例区分，不将空断言或未实现步骤加入 dev 执行清单。

每例围绕一个业务目标，可包含完整跨端链路。浏览器与客户端通过同例上下文传递精确测试数据，不依赖另一例执行顺序和遗留登录状态。

## 用例列表维护

用例列表是给人阅读的已实现 E2E 目录，不是本次 dev 执行清单，也不是测试运行报告。优先维护项目已有的列表文件或生成入口；项目没有列表时，建立 `tests/e2e/CASE_CATALOG.md`。只维护这一份权威目录，避免另建重复列表。

以测试源码和 Runner 实际收集结果为依据，每行至少包含：稳定编号、业务模块、具体名称/验证目标、运行端、smoke/regression 集合和源文件链接。列表说明当前可执行用例总数；有模块分组或数量统计时同步更新。不能把草稿、计划用例或示例接入测试写成产品已实现覆盖，也不能在目录中写无依据的“已通过”。

| 变更 | 必须同步的内容 |
|---|---|
| 新增正式用例 | 增加真实编号、名称、模块、运行端、集合和链接，更新总数 |
| 删除用例 | 从当前列表移除，更新总数，清除 dev 等执行清单的失效编号；不回收编号 |
| 改名、移动文件或模块 | 保留编号，更新名称、归属和源文件链接 |
| 修改测试行为或标签 | 更新验证目标、运行端和集合，不能保留过时的覆盖声明 |

若列表由脚本生成，运行现有生成器，不手改生成结果。若为手写 Markdown，基于收集结果更新相关行和统计；无需为了维护列表另外造一套测试管理系统。已有历史编号映射按原规范保留，历史报告不修改。

完成前全量离线收集，核对列表与可执行集合的 ID、数量、元数据和文件链接一致，检查遗漏、重复、失效链接和已删除编号的执行引用。删除导致 dev 清单为空时明确报告，并遵循项目显式跳过或报错规则，不自动挑其他用例补满、不扩大执行范围。用例集合变化影响已有冒烟/回归范围时说明覆盖变化。

列表同步属于本次 E2E 修改的完成条件，即使未要求准备 dev/release 也要执行；选择本次完整验证范围则依据任务要求，不把全部新增用例自动加入所有集合。没有业务环境时仍可完成列表和引用校验，实机结果单独标明未验证。

## 前置、动作、断言与清理

前置条件必须保证被测动作可执行。例如“首次准入”应准备待准入资源，不能发现已准入就跳过动作仍称通过；“确保在线”才允许复用已准入状态。准备与清理只操作本次创建或明确专用的资源。

默认让 Midscene 主导可见 UI 操作。提示词明确区域、唯一目标和完成状态，例如等待添加窗口可见，再点击窗口内的待准入标签，随后确认对应面板内容。不要只说“点那个 tab”，也不要在提示词里写易失效的固定坐标。

API 可创建数据、核验结果及清理，不能代替正在验证的 UI 操作。登录若是前置可以用公共节点；登录若是被测功能就必须执行实际登录流程。密码由项目安全输入机制填写，不写进 YAML、模型提示词或日志。

断言应定位精确目标，检查明确业务结果，如所属用户、唯一资源、在线状态或持续推进的心跳时间。页面能打开或 HTTP 200 不证明业务成功。异步变化采用带截止时间的条件等待，不随意追加固定休眠、重复点击或自动重试来掩盖缺陷。

在跨端用例中明确哪个节点控制浏览器、哪个控制客户端。桌面操作前确认实际窗口就绪且目标正确；进程存在不是界面可用的充分证据。取消/超时后应停止后续动作，遵循框架取消信号及资源释放机制，避免旧请求操纵下一例。

资源创建后立即登记清理，断言失败也清理；只清理本例资源，不按通用名称删除其他数据或进程。清理错误记录到执行结果，不能吞掉。

## 可视报告与验证

复用项目的报告包装和截图记录能力。Midscene 操作保留视觉记录；必要的 Playwright/API 核验步骤应保留说明及相关页面截图，避免改成确定性操作后报告只剩文字。截图失败与原始操作失败分别保留，不能让截图错误遮住原失败。

同例两端操作归入同一次尝试的报告，以 Runner ID 和步骤关联，不按文件时间猜测归属。总览能从编号、名称和源文件定位操作报告；准备、业务动作、清理、失败及未执行步骤均可解释。

修改 YAML 后做收集和选例检查；新增 Node 后做类型及 schema 检查；修改报告后用浏览器验证实际截图与跳转。只能收集成功不代表业务通过。实机运行须确认部署版本及专用数据，报告中区分产品断言、脚本、模型与环境故障。

按已确认计划设置集合标签，验证新用例被真实执行入口收集。任务包含准备 dev 验证时，将新例和需要复用的已实现 ID 写入 dev 清单并预览。实现中需要实质改变测试目标或覆盖范围时，先展示设计差异并确认后再修改，不在实现完成后补通知。
